Didi ka Playground

A voice chatbot that simulates the GramStack shared layer. A didi asks a question in her own language. The assistant works out which of her records it needs and asks her consent, in her language, before reading them. It then fetches only those fields from a connected sheet or database, answers, and discards the data.

Prepared by Karan J with Claude Status M1 built · M2 next Based on GramStack note for MoRD (Sept 2026) and bhashini_kit
Decided
  • This document comes first. The build starts after review.
  • The first demo is in Hindi. Other languages come later.
  • Data comes from an uploaded Excel file, a Google Sheet link, or a SQL connection string. There is no Google sign-in.
  • "Decision model" means a rules or decision-table engine that the agent calls as a tool.
  • We write the mock registers: a LokOS-shaped workbook with 8 didis, 7 of them Hindi speakers.
  • LLM calls use a free-tier NVIDIA key, so the design keeps the number of calls low (§10).
  • A dropdown in the operator panel sets whether the didi sees the steps behind an answer (§3).
  • Business-plan unit costs are mock figures in JEEViKA (Bihar SRLM) format, labelled as mock until real JEEViKA norms replace them (§7).
  • Consent is per question only. No grant carries over to a later question, and the operator has no setting to change that (§4.1).
  • Hosting is Vercel. Agent runs pause and resume across function calls, and state lives in Postgres and Vercel Blob (§11).
  • A department view shows each source's owner every access to its system and lets it pause the source (§3).
What this design recommends
  1. Consent is enforced in a tool gateway, in code. A prompt alone cannot enforce it.
  2. Each question that needs her records gets one consent prompt. The prompt is itemised, spoken in her language, and treats an unclear answer as no.
  3. Lakhpati status and bank-linkage readiness come from decision tables. The LLM gathers the inputs and explains the result.
  4. The default agent is Plan-and-Execute on native tool calls. ReAct and four other agent types can be picked for comparison.
  5. Business plans are built by code from validated assumptions, and the Excel formulas stay live.

2The didi's journey

  1. LandingWhat the playground is, and one button to start.
  2. Connect dataUpload Excel, paste a Google Sheet link, or enter a SQL URL. Label fields and set the consent wording.
  3. Log in as a didiPick her from the users tab. This stands in for Aadhaar authentication.
  4. AskShe taps the big mic and speaks, or types.
  5. ConsentIf her records are needed, she hears what will be read, why, and for how long, then answers in her own words.
  6. AnswerSpoken and written in her language, with the registers it came from. The fetched data is then discarded.

How the chat behaves

  • The mic button is 84 px, centred above the text box, where a thumb reaches it. Tapping it starts bhashini.startRecording({autoStop: true}), which stops 1.3 s after she stops speaking. Its states are idle, listening (the ochre ring shows the input level), transcribing, and speaking (tap to stop playback).
  • Her words appear in a bubble and are sent straight away, with "फिर से बोलें" (speak again) to redo them. The operator can switch on "review transcript before sending" for noisy rooms.
  • Answers are spoken with bhashini.speak() by default, and ▶ replays them.
  • Typed Latin-script Hindi such as "haan theek hai" is transliterated with bhashini.transliterate() before it is interpreted.
  • Evidence chips under each answer name the register and period. This lets her spot a stale or wrong record (MoRD note §5.1).
  • Steps shown to the didi are set from a dropdown in the operator panel: Hidden (the default), Collapsed under each answer (as in the mock), or Open under each answer. Her version is a short list in Hindi of what was done, with no model names, prompts or raw values. It is built from the trace events with fixed Hindi templates, so it costs no LLM call.
  • The operator panel is a right column on desktop and a sheet behind a settings button on phones. It always shows the full trace, whatever the dropdown says.

4Consent

The note says consent is taken "where the citizen already proves who she is", stated "in her own language", and is "specific to a purpose, logged, and withdrawable". The playground follows those rules and adds two things the user brief asks for. The didi can answer in her own words, and the operator can change both the consent wording and the phrases that count as yes or no.

4.1 When the assistant asks

SituationConsent?Why
General question ("What is Lakhpati Didi?")NoAnswered from curated scheme notes. None of her records are read.
Reading table and field namesNolist_sources returns the schema only, never values.

A field she refused earlier in the sessionNot asked againRefusals are remembered for the session. The agent is told not to request the field unless she brings it up.
Group records (SHG meetings, group loans)Office bearerOnly a didi whose users row has role president, secretary or treasurer can consent for the group. MoRD note §5.4 leaves the real rule to an administrative decision.
Building a business planYesOne bundled prompt for everything the plan template reads.

4.2 What she hears

Each prompt is built from four parts, and each part is spoken: what will be read (itemised, with the register name), why (one stated purpose), how long (this question, then deleted), and the question. The chat mock above shows the Hindi card. The field labels and register names come from the setup step, so the prompt never shows raw column names like dar.expense.

4.3 Reading her answer

  1. Button. हाँ, नहीं or कुछ ही दिखाइए gives a definite decision. "Show only some" turns the items into toggles.
  2. Voice or text. The answer goes through ASR in her language, or is transliterated if she typed in Latin script, then normalised (nukta, chandrabindu, spacing).
  3. Vocabulary match. The answer is checked against the yes, no, partial and why phrases for her language, including the operator's custom phrases. A match decides the answer without an LLM call.
  4. LLM interpreter. If nothing matches, a small fast model returns strict JSON: decision, fields_granted, fields_refused, asked_why, confidence.
  5. Read-back. A partial grant or confidence below 0.8 is read back to her: "आपने कहा '…'। मैं समझी कि आप सिर्फ़ बचत दिखाने की अनुमति दे रही हैं। क्या यह सही है?" (You said '…'. I understood you are allowing only savings to be shown. Is that right?)
  6. Default deny. If she is still unclear after two tries, the answer is no. Nothing is fetched on an unclear answer.

4.4 Her own words: the consent vocabulary

Each language has a default phrase list. The operator can add phrases that didis in a district actually use, including dialect words. A custom phrase takes priority over the LLM, so the result is predictable and can be audited.

5Agents and tools

5.1 The need check

Before any tool runs, every agent decides whether the question is general (no records needed), personal (her records needed, so consent is required) or an action (such as building a plan, which also needs consent). Plan-and-Execute does this in its planner, ReAct in its first thought, and native tool calling by choosing tools. The decision catalogue gives a deterministic hint: if the question matches a decision such as lakhpati_status, the inputs that decision needs define what to ask for.

In pivot mode, amounts, dates and names are swapped for placeholders before translation and restored afterwards, so NMT cannot garble ₹1,24,800 or a name. Names are found with bhashini.entities(). Each language gets a default mode, and the compare view can run direct against pivot.

5.7 Recommendation

Default: Plan-and-Execute on native tool calls, with the self-check critic on whenever the answer contains numbers. It asks the didi once per question and reads the fewest fields, which matters more to her than a second saved.

Fallback: ReAct for models that fail the tool-call probe, and for open-ended questions where the plan cannot be known up front.

Baseline: Direct, kept in the compare view to show what an LLM says without her consented data.

6Decision tables as tools

YES

A decision model works well as a tool, and the playground should use one. Eligibility, readiness and status are rules a department publishes. They must give the same answer every time, carry a version, and be explainable rule by rule. An LLM working these out itself would be neither repeatable nor auditable. So the LLM gathers inputs (with consent) and explains the result in her language, and the decision table decides.

6.1 How it plugs into the agent

  1. The need check matches the question to a decision, for example lakhpati_status.
  2. describe_decision returns the inputs and the source fields behind them. That list becomes the consent request, and the decision's stated purpose becomes the purpose. Consent is therefore exactly as wide as the rule needs.
  3. The agent fetches the fields, derives inputs with calculate, and calls decide.
  4. The tool returns the outcome, the matched rule, reasons in English and in her language, the table version, and any missing inputs.
  5. The LLM explains the result. It cannot change the outcome, because the critic checks that the stated outcome matches the tool's output.

6.5 Authoring and engine

  • Decision tables are stored as JSON in decisions/. Optionally, a decisions tab in a connected workbook can hold them, because the people who maintain rules already work in Excel. Each table has an id, a version, a hit policy, inputs (each with a derive expression over source fields), rules and annotations.
  • A small Python evaluator handles the UNIQUE, FIRST and COLLECT hit policies and a subset of FEEL comparisons (<, ≥, ranges like [60000..100000), lists, and – for any value). That covers these tables with no extra dependency.
  • DMN 1.3 XML import can come later. One option is to evaluate pyDMNrules, which reads DMN-style tables from Excel. That would be decided in M5, and nothing depends on it.

7Business plan builder

Asked "मेरी डेयरी बढ़ाने का बिज़नेस प्लान बना दो" (make a business plan to grow my dairy), the agent builds an Excel workbook from her registers. The LLM only proposes assumptions. Code builds the workbook, and every number in it is either an input cell with a stated source or a live formula.

7.1 Flow

  1. Identify the enterprise type and whether it already exists (from the enterprise register) or is new.
  2. Ask once for consent covering what the template reads: DAR income and expense, the enterprise row, loans and savings. For Sunita, loans were refused earlier in the session, so the agent asks about loans separately and says why.
  3. The LLM proposes an assumptions JSON from her data and the mock JEEViKA unit costs. A Pydantic schema validates it for units and plausible ranges.
  4. Two or three key assumptions are confirmed by voice: "रजिस्टर में हर गाय का रोज़ 8 लीटर दूध दर्ज है। क्या यह सही है?" (The register shows 8 litres a day per cow. Is that right?)
  5. openpyxl writes the workbook from the template and sets it to recalculate fully when opened, because LibreOffice cannot run on Vercel. The figures spoken in chat are computed in Python from the same formulas. In CI, a test recalculates sample workbooks with LibreOffice and checks the two agree.
  6. Chat shows a download card and speaks a three-line summary.

9Connecting data

Upload Excel

Read with openpyxl. Each tab is a table, and row 1 holds the headers. The file is stored in Vercel Blob. Files over 4.5 MB upload straight from the browser to Blob.

Google Sheet link

The sheet id is parsed from the link. If the sheet is shared with the playground's service account, it is read through the Sheets API. Otherwise each tab is read through the public CSV export. A public link gets the warning "anyone with this link can read it; use only for mock data".

SQL database

A Postgres URL that Vercel can reach (so not a database on a laptop), or an uploaded SQLite file, which is copied from Blob to /tmp for each call. SQLite opens with mode=ro, and Postgres sessions are read-only transactions. Tables are allow-listed and queries parameterised. The agent never writes SQL.

Setup steps after connecting

  1. Detect tables and columns, and show 5 sample rows.
  2. For the first source, pick the users table and the didi_id column. For later sources, pick the join key (didi_id or household_id).
  3. Name the department that owns the source, for the department view (§3). Then label each field in each language and set its sensitivity (§4.5).
  4. Edit the consent template and vocabulary, then preview them aloud.
  5. Test one fetch for one didi, which goes through the gateway and is logged.

Every connector implements the same interface: tables(), users(), fetch(table, fields, key, value). Only the gateway calls fetch.

10Models on NVIDIA

LLM calls go to https://integrate.api.nvidia.com/v1/chat/completions, which is OpenAI-compatible. The NVIDIA_API_KEY stays on the server, following the same rule as the Bhashini key in bhashini_kit. The model dropdown is filled from GET /v1/models. On 15 October 2026 that endpoint listed 81 models, including embedding, safety and vision models, which the dropdown hides.

Not every chat model supports tool calls. The server probes each model on the shortlist below with one small tool-call request, caches the result on disk, and marks the model native tools ✓ or text only. Other models are probed only when someone picks them. Text-only models still run ReAct and ReWOO, which use our own text protocol.

Working within a free-tier key

The playground uses a free-tier key. Free-tier keys are rate-limited and meant for development, so the design keeps LLM calls down:

  • The consent vocabulary is checked before the LLM interpreter, so a plain हाँ or नहीं costs no call.
  • The self-check critic runs only on answers that contain numbers.
  • Compare mode adds one agent by default and runs it after the first, never at the same time.
  • Every request backs off and retries on HTTP 429, and the chat shows "थोड़ा रुकिए" (please wait a moment) instead of an error.
  • A demo cache records each run's LLM responses, keyed by model and prompt. In demo mode, a rehearsed question replays from the cache if the API is throttled on the day. The trace marks replayed steps.
